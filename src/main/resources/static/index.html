🗄️ Database Integration

The Unified QA Runner can be integrated with databases using the database-connection-management agent skill available in JetBrains IDEs (DataGrip, IntelliJ IDEA Ultimate). This skill enables AI agents to set up, manage, and test database connections directly from the IDE.

What Is Database Connection Management?

The database-connection-management skill provides step-by-step instructions for AI agents to:

  • Create new data sources — Build JDBC URLs, configure connection details, and verify connectivity.
  • Edit existing connections — Update host, port, username, password, or other connection parameters.
  • Test connections — Run connection tests to diagnose and fix broken connections.
  • List configured data sources — Discover all existing database connections in your project.
  • Diagnose connection issues — Analyze error messages and suggest fixes for common problems.
💡 How It Works: The skill uses MCP (Model Context Protocol) tools like create_database_connection and edit_database_connection to interact with your IDE's database tools. No additional setup is required — the tools are bundled and enabled by default.

How to Set Up a Database Connection

Option 1: Using AI Chat (Recommended)
  1. Open the AI Assistant chat in your JetBrains IDE (DataGrip or IntelliJ IDEA Ultimate).
  2. Type a request like: "Create a PostgreSQL connection to localhost:5432/mydb with user admin"
  3. The AI agent will:
    • Collect any missing connection details
    • Build the correct JDBC URL
    • Create the data source in your IDE
    • Run a test connection to verify it works
  4. The new data source appears in the Database Explorer panel immediately.
Option 2: Manual Setup via IDE
  1. Open the Database tool window: View → Tool Windows → Database
  2. Click + → Data Source → Select your database type
  3. Fill in the connection details:
    • Host: Server address (e.g., localhost or db.example.com)
    • Port: Database port (e.g., 5432 for PostgreSQL, 3306 for MySQL)
    • Database: Database name
    • User: Username for authentication
    • Password: Password for authentication
  4. Click Test Connection to verify the connection works
  5. Click OK to save the data source

Using Database Connections in Test Scripts

Once a database connection is configured, you can use it in your test scripts for data setup and verification:

Java Example (JDBC)
String url = "jdbc:postgresql://localhost:5432/mydb";
String user = "admin";
String password = "secret";

try (Connection conn = DriverManager.getConnection(url, user, password)) {
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT * FROM users");
    while (rs.next()) {
        System.out.println(rs.getString("name"));
    }
}
Cucumber Step Example
@Given("the user exists in the database")
public void userExistsInDatabase() throws SQLException {
    String sql = "INSERT INTO users (name, email) VALUES (?, ?)";
    try (Connection conn = DriverManager.getConnection(url, user, password);
         PreparedStatement pstmt = conn.prepareStatement(sql)) {
        pstmt.setString(1, "Test User");
        pstmt.setString(2, "test@example.com");
        pstmt.executeUpdate();
    }
}

Common Connection Issues & Fixes

❌ "Connection refused" error ▼

Cause: The database server is not running or the host/port is incorrect.

Fix:

  • Verify the database server is running: systemctl status postgresql (Linux) or check Services (Windows)
  • Check the host address — use localhost for local databases
  • Verify the port number matches your database configuration
  • Check firewall settings if connecting to a remote server
🔑 "Access denied" or authentication failed ▼

Cause: Incorrect username or password, or the user doesn't have permission to connect.

Fix:

  • Double-check the username and password for typos
  • Verify the user exists in the database: SELECT * FROM pg_user; (PostgreSQL)
  • Check that the user has the correct privileges for the target database
  • For PostgreSQL, check pg_hba.conf for authentication method
📦 "Driver not found" error ▼

Cause: The JDBC driver for your database is not installed or configured.

Fix:

  • For bundled drivers (PostgreSQL, MySQL, SQL Server, MongoDB, Redis), the IDE should auto-download them
  • For other databases, download the JDBC driver JAR and add it to the classpath
  • In DataGrip, go to File → Settings → Project → JDBC Drivers and add the driver
  • Ensure the driver version is compatible with your database version
🔒 SSL/TLS connection errors ▼

Cause: The database requires SSL but the connection doesn't have the correct certificates.

Fix:

  • In the data source settings, go to the SSL tab
  • Enable SSL and configure the certificate path if required
  • For development, you may disable SSL (not recommended for production)
  • For cloud databases (AWS RDS, Azure SQL), download and configure the CA certificate

Database connections can be integrated with various test frameworks for data-driven testing:

⚠️ Best Practices:
  • Use connection pooling (HikariCP, DBCP) for better performance in test suites
  • Close connections properly using try-with-resources to avoid leaks
  • Use separate test databases to avoid contaminating production data
  • Roll back transactions after each test to maintain a clean state
  • Store connection details in environment variables or config files, not in code

🚪 API Gateway Integration

The Unified QA Runner can test API Gateway configurations directly from shared paths. Place any API Gateway spec file in a shared path or tests/apigateway/ directory, and the plugin will auto-discover and execute all endpoints.

What Is API Gateway Testing?

API Gateway testing validates that all endpoints defined in your API Gateway configuration are accessible and responding correctly. The plugin parses your gateway spec, extracts all endpoints, and executes HTTP requests against each one.

Supported Formats

FormatFile ExtensionDescription
OpenAPI 3.x.yaml, .jsonModern OpenAPI specification with paths and servers
Swagger 2.0.yaml, .jsonLegacy Swagger specification format
AWS API Gateway.yaml, .jsonAWS API Gateway REST API exports with x-amazon-apigateway extensions
Azure API Management.yaml, .jsonAzure APIM exports and configurations
Postman Collection.jsonPostman collection v2.1 format with nested folders
Generic Gateway.yaml, .jsonAny file containing "gateway" or "api-gateway" in name/content

How to Use

  1. Create an API Gateway spec file — Use OpenAPI/Swagger format or export from your gateway tool.
  2. Place it in a shared path — Drop the file in tests/apigateway/ or any configured shared path.
  3. Open the app — Go to http://localhost:8081/ and select the API Gateway asset from the asset picker.
  4. Set the target URL — The base URL is auto-extracted from the spec's server definition, or enter your gateway URL manually.
  5. Click "▶ Run" — The plugin executes HTTP requests against each endpoint and generates a report.

Sample OpenAPI Spec

openapi: 3.0.3
info:
  title: My API Gateway
  version: 1.0.0

Key Features

  • Auto-discovery — Scans tests/apigateway/ and all shared paths for gateway configs.
  • Auto URL extraction — Reads the server URL from OpenAPI spec automatically.
  • Path parameter resolution — Replaces {id} parameters with sample values.
  • Collection support — Run multiple gateway configs in a single execution.
  • Report generation — Generates text and JUnit XML reports for CI/CD integration.
  • No dependencies — Uses Java HttpClient, no external tools needed.
✅ No Setup Required: Unlike other frameworks, API Gateway testing needs no external dependencies. Just place your spec file in the shared path and run — the plugin handles everything.

Troubleshooting

❌ Endpoints return 404

Check that the target URL matches your API Gateway base URL. The plugin auto-extracts the URL from the spec's servers section, but you can override it manually.

❌ Config file not discovered

Ensure the file contains API Gateway indicators like openapi:, swagger:, paths:, or gateway in the filename/content. Place it in tests/apigateway/ or a configured shared path.

❌ Connection timeout

The plugin uses a 30-second connection timeout. If your gateway is slow, ensure the network is reachable. Check firewall rules and gateway status.

🏗️ Challenges Faced During Development

Building the CI/CD Integration was the most challenging part of this project. Here's a timeline of the issues we encountered and how we resolved them:

1. JSON Serialization Issues
Bug The JsonParser.parse() method returned raw Object types, causing unsafe cast errors when working with Map<String, Object> in CI/CD config and pipeline status services.
Resolution: Changed all pattern matches from Map<String, Object> to Map<?, ?> and updated helper method signatures to accept wildcard types.
2. GitHub URL Format Handling
Bug Users entered full GitHub URLs like https://github.com/owner/repo.git, but the API expected owner/repo format, causing "Repository not found" errors.
Resolution: Added normalizeRepoUrl() method on both client and server sides to strip URL prefixes and .git suffixes automatically.
3. GitHub Token Permission — The 403 Error
Critical The biggest challenge! GitHub tokens with only the repo scope could read repositories but failed with HTTP 403 when committing to .github/workflows/. GitHub requires the workflow scope specifically for workflow files.
Resolution: Updated error messages to clearly explain the missing scope requirement and provided step-by-step token regeneration instructions.
4. Classic Token "workflow" Scope Grayed Out
Critical GitHub only enables the workflow scope on classic tokens when Actions is already active on a repository. New repos had the scope permanently disabled.
Resolution: Guided users to enable Actions first by committing a placeholder workflow, then regenerating the token. Also added Fine-grained token as an alternative.
5. Fine-Grained Token Missing Permissions
Critical Fine-grained tokens use a different permission model. Even with "Contents → Read & write", commits to .github/workflows/ still failed because Actions and Workflows permissions were also required.
Resolution: Discovered through git command-line testing that all three permissions (Contents, Actions, Workflows) must be set to "Read & write". Updated the token help guide accordingly.
6. Git Command-Line Fallback
Enhancement The GitHub REST API sometimes blocked fine-grained tokens even with correct permissions. The git command line worked better in some cases.
Resolution: Implemented a dual-commit strategy: try git command line first, then fall back to the GitHub REST API if git is unavailable.
7. Schedule Picker Hour/Minute Bug
Bug The visual schedule picker swapped hours and minutes — entering 00:12 displayed as "Runs at 12:00" instead of "Runs at 00:12".
Resolution: Fixed the variable assignment order in updateCiCdCronPreview() — HTML time inputs return HH:mm, so parts[0] is hours and parts[1] is minutes.
8. UI Result Visibility
UX Enhancement Users couldn't see the results of CI/CD actions (test connection, save config, download, commit) because messages auto-hidden after 8 seconds.
Resolution: Replaced auto-hiding messages with persistent result panels that stay visible until manually closed, showing detailed information like platform, repository, branch, and frameworks.

🔑 GitHub Token Setup — Complete Guide

This was the most confusing part for users. Here's everything you need to know:

Option 1: Classic Token

⚠️ Limitation: The workflow scope may be grayed out if you haven't enabled GitHub Actions on any repository yet.
  1. Go to github.com/settings/tokens
  2. Click Generate new token → Generate classic token
  3. Name it: QA Runner
  4. Check both scopes: repo AND workflow
  5. Click Generate token and copy the token (starts with ghp_)

Option 2: Fine-Grained Token (Recommended)

✅ Recommended: Fine-grained tokens don't have the grayed-out scope issue and provide more granular control.
  1. Go to github.com/settings/tokens?type=beta
  2. Click Generate new token
  3. Name it: QA Runner
  4. Under Repository access, select All repositories or your specific repo
  5. Click + Add permissions and set all three:
    • Contents → Read & write (for committing files)
    • Actions → Read & write (for running workflows)
    • Workflows → Read & write (⚠️ required for .github/workflows/)
  6. Click Generate token and copy the token (starts with github_)
🔑 Critical Reminder: You must set all three permissions (Contents, Actions, Workflows) to "Read & write". Missing any of these will cause a 403 error when committing workflow files. This was the hardest lesson we learned during development!

🔧 Troubleshooting Common Issues

❌ "Repository not found" error ▼

Cause: Typo in the repository URL or the token doesn't have access to the repository.

Fix:

  • Double-check the repository URL — common mistake: chandan94 instead of chandran94
  • Verify your token has the repo scope (classic) or "Contents" permission (fine-grained)
  • Any URL format works: owner/repo, https://github.com/owner/repo.git, etc.
🚫 HTTP 403 Forbidden when committing ▼

Cause: Your GitHub token is missing the required permissions for .github/workflows/.

Fix:

  • Classic token: Ensure both repo AND workflow scopes are checked
  • Fine-grained token: Ensure Contents, Actions, AND Workflows are all set to "Read & write"
  • Regenerate the token with the correct permissions and re-save it in the CI/CD form
⚠️ Most common mistake: Having "Contents → Read & write" but missing "Actions" or "Workflows". All three are required!
🔒 "workflow" scope is grayed out ▼

Cause: GitHub only enables the workflow scope when Actions is active on at least one repository.

Fix:

  • Go to your repo's Actions tab and enable Actions by committing any workflow file first
  • Or use a Fine-grained token instead (recommended) — it doesn't have this limitation
⏳ Server hanging on commit ▼

Cause: The saved token in qa-runner.json is corrupted or from a previous encryption.

Fix:

  • Re-save your CI/CD configuration by pasting the token again and clicking "Save Config"
  • This replaces the old corrupted token with a fresh encrypted one
📅 Schedule showing wrong time ▼

Cause: The schedule picker was swapping hours and minutes (bug, now fixed).

Fix: The bug has been fixed. Enter the time in the format HH:mm (e.g., 00:12 for 12 minutes past midnight). The cron expression and description will update live.
